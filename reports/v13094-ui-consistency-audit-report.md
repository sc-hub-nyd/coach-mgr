# CoachMgr UI一貫性監査報告

**監査日:** 2026-08-20  
**対象バージョン:** v1.30.94  
**対象:** ボタン、通知、カード、ナビゲーション、モーダル、状態表示、ライト／ダーク表示

## 結論

重大な操作不能や、危険操作と通常操作を誤認させる**P0の問題は確認されなかった**。直近で指摘された練習カードの共有操作縮小、その他メニュー面の角張り、PWA更新ボタンの赤・緑混在は、それぞれv1.30.93およびv1.30.94で解消済みである。

一方で、チームカラーを変更できるという設計方針に対して、`base.css`に固定の赤・緑・青が残っている。選択中ナビゲーション、モバイルボトムナビ、ロール切替、同期ステータス、スケジュール種別にその影響があり、**現時点で最も優先すべき視覚的一貫性の課題**である。また、共通ボタンを経由しないモーダル閉じる操作にはhover・focus-visibleの状態規則がなく、キーボード利用時の認知性を改善する余地がある。

| 判定 | 件数 | 内容 |
|---|---:|---|
| P0 | 0 | 直ちに操作停止・誤操作を招く問題は未検出。 |
| P1 | 3 | セマンティックカラーの迂回、モーダル閉じる操作の状態不足、強制上書きの集中。 |
| P2 | 3 | 角丸尺度の揺れ、共通部品外ボタン、空状態での主操作重複。 |
| P3 | 1 | 微細な影・余白・コンテナの整理候補。 |
| 解消済み | 3 | 練習操作均等化、その他ボトムシート角丸、PWA更新通知の成功トーン化。 |

## 実画面で確認したこと

保護者モードのダッシュボード、試合記録、練習管理をライト／ダークの両方で確認した。試合・練習の検索列、絞り込み、空状態surfaceは共通構造と角丸・罫線・余白が揃っている。練習空状態の補足文はライトで**5.54:1**、ダークで**7.86:1**、見出しはライトで**14.56:1**、ダークで**19.27:1**の実効コントラストであり、控えめな視覚表現ではあるが本文の可読性基準は満たしている。

コーチモードはパスコードを必要とするため、解除を試行せず、コーチ専用の実データ画面は静的CSS、テンプレート、既存の実画面証跡で確認した。したがって、以下のP1・P2は推測ではなくソース上の具体的な実装根拠を持つが、コーチ専用の全データ量・全画面状態を同一端末で視覚確認したものではない。

## P1: チームカラーに追従しない固定色

`base.css`には固定の赤、緑、青が53件残っている。画面・部品層の直接指定色が0件という既存監査とは矛盾しない。これは基盤層を対象外としているためだが、利用者から見れば基盤か画面かは区別されない。特に選択状態やステータスに使われる固定色は、チームカラーの変更後に「カードや主要ボタンは新チームカラーなのに、ナビだけ赤い」という違和感を生む。

| 対象 | 現在の実装 | 問題 | 改善方針 |
|---|---|---|---|
| PCサイドバー選択・hover | `rgba(242, 57, 50, 0.08)`、`var(--primary)` | soft surfaceだけが既定の赤に固定される。 | `--color-surface-selected`へ統一する。 |
| モバイルボトムナビ選択・その他展開 | `rgba(242, 57, 50, 0.08) !important` | チームカラー変更時も赤い選択面が残り、強制指定のため局所修正も阻害する。 | 選択面トークンと専用状態クラスへ置換し、`!important`を段階的に撤去する。 |
| 保護者／コーチ切替 | 固定の緑、赤、濃緑 | ロールの意味とチームブランドの意味が具体色に結び付いている。 | `--color-success-*`、`--color-brand-*`、`--color-text-*`の役割トークンへ置換する。 |
| 同期ドット | `#22c55e`、`#ef4444`、`#3b82f6`と固定shadow | light/darkや将来テーマで同一の明度・影が残る。 | success／danger／infoのsurface・border・shadowトークンを用意する。 |
| 予定チップ | 練習は固定の青、試合とhoverは固定赤 | 種別ラベルがチームカラーや状態表現と競合する。 | `--color-info-*`、`--color-brand-*`、選択surfaceトークンを使う。 |

この項目は、色の好みを変える修正ではない。**意味を色役割へ戻す修正**であり、任意のチームカラー、ライト／ダーク、将来のテーマ追加に対する耐性を回復する。

## P1: モーダルの閉じる操作に状態規則がない

共通の`.c-modal__close`は44pxの操作領域と角丸を持つ一方、hover・focus-visible・activeの専用規則を持たない。さらに多くの閉じる操作は`.c-button`を付与しないため、`.c-button:focus-visible`の共通リングも適用されない。マウスでは控えめな見た目を維持できるが、キーボードやスイッチ操作では、現在どの閉じる操作に焦点があるかが判別しづらい。

改善では、`.c-modal__close`へneutral surfaceのhover、`--color-focus`を用いたfocus-visible、押下時のpress表現、disabled時の統一規則を追加する。浮動型のcloseにも同一規則を適用し、位置だけを`.c-modal__close--floating`で変えるべきである。

## P1: 強制上書きが視覚回帰を起こしやすい

静的集計では`!important`が`base.css`に171件、`dashboard.css`に114件、`components.css`に45件存在する。モバイルボトムナビだけでも表示、サイズ、色、背景、角丸の大半が強制指定されている。直近の「その他」や練習操作の修正で経験したように、一般規則が局所規則を上書きする、または逆に新しい規則が既存状態を上書きできない状況を生みやすい。

この項目は直ちに見た目を変更しない。ただし、P1の固定色移行と同時に、モバイルナビ・コンテキストバー・ダッシュボードの上書きを**層順とセレクタ詳細度**で解決できる形へ縮小する必要がある。これが「直したのに別端末では戻る」という再発を減らす。

## P2: 形状尺度の揺れ

標準コンポーネントは`--radius-sm`、`--radius-md`、`--radius-lg`、`--radius-pill`、`--control-radius`を持つ。しかし画面CSSには4px、6px、8px、10px、12px、14px、16px、20px、22pxの直書きが広く残る。すべてが誤りではない。例えば、線グラフ、ピッチ上の記号、片側だけ丸める分割操作は例外として合理的である。

問題は、カード、チップ、設定行、ダッシュボードの小面、作図ツールバーまで同じ種類のsurfaceが別々の半径を使うことにある。カード系は`--radius-lg`、標準操作と入力は`--control-radius`、バッジ・小チップは`--radius-sm`、接続された分割操作だけが片側半径を持つ、という4段階へ整理する。`dashboard.css`、`drawing.css`、`tactical.css`に残る固定半径はこの基準で台帳化する。

## P2: 共通ボタンを経由しない操作

`dash-action-item`、`c-data-list__item--button`、`c-status--interactive`、`btn-side-remove-pk`、モーダルcloseなどは、通常の`.c-button`とは別系統の操作である。データ行やステータスタグを押せるようにすること自体は適切だが、各系統がhover、focus-visible、active、disabledを独自に実装しているため、状態ごとの影、移動量、フォーカスリングが揃いにくい。

改善では操作を「主要ボタン」「副ボタン」「危険ボタン」「アイコンボタン」「行ボタン」「ステータスタグ操作」の6種へ分類し、各種に最低限の状態契約を定義する。`c-static-style--006`のような用途名を持たない特殊操作は、危険アイコンボタンなど意味のある部品名へ移す。

## P2: ダッシュボード空状態の主操作重複

保護者モードのダッシュボード空状態では、「次の予定」と「直近の試合」の双方に同じ「試合を追加」が現れる。意図は理解できるが、データがない初期状態では主操作が二つ並び、どちらから始めるべきかの優先度が薄くなる。

改善案は、上部の「次の予定」を主導線として残し、下部の「直近の試合」は説明と一覧導線だけにすることである。コーチモードでは「試合追加」と「練習追加」を一つの明示的な作成導線へまとめ、空状態カードは作成先ではなく情報の役割を優先する。

## P3: 影・余白・legacy規則の整理

黒のRGBA影や既定値fallback、画面固有の小さな余白指定が基盤CSSに残る。これらは現時点で明確な視覚障害を起こしていないが、P1・P2の移行と一緒に`--color-shadow-*`、space token、radius tokenへ寄せるべきである。変更対象を一括で置換せず、ナビゲーション、状態表示、ダッシュボード、作図の順に回帰確認しながら進める。

## 推奨ロードマップ

| フェーズ | 優先度 | 実装範囲 | 完了条件 |
|---|---|---|---|
| A. 状態色の意味統一 | P1 | sidebar、bottom nav、role toggle、sync dot、schedule badge | 固定の状態色を役割トークンへ置換し、light/darkと3種のチームカラーで状態面が連続する。 |
| B. 非標準操作の状態契約 | P1 | modal close、行ボタン、ステータスタグ、危険アイコン | 全操作種にhover・focus-visible・active・disabledの最小契約を持たせる。 |
| C. 上書き縮小 | P1 | mobile nav、context bar、dashboard | 色・角丸・サイズについて不要な`!important`を削減し、詳細度の高い専用規則へ置換する。 |
| D. 形状尺度の統合 | P2 | dashboard、drawing、tactical、components | 4段階のradius尺度にマッピングし、例外だけを台帳化する。 |
| E. 主操作の整理 | P2 | dashboard初期状態、空状態、作成導線 | 1領域につき主操作を一つにし、重複CTAを削減する。 |

## 再発防止

P1では、固定の`#`・`rgb`・`rgba`を基盤層も含めて監視する監査を追加する。ただしCanvasや媒体プレビューの正当な例外は明示的な許可リストへ移す。P1・P2の操作系には、通常・hover・focus-visible・active・disabledの各状態を静的契約として追加する。さらに、390pxとデスクトップ幅、light/dark、赤・青・緑のチームカラーでスクリーンショット比較を行う視覚回帰シナリオを追加する。

## 監査上の制約

監査は公開PWA v1.30.94、リポジトリ全CSS、既存の品質テスト、保護者モードの実画面、利用者が提示した実データ画面証跡を対象とした。コーチ専用の実データ画面は、監査ブラウザにパスコードがないため操作・変更を行わず、静的レビューに限定した。
