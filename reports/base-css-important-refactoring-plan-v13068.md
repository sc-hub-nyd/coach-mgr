# base.css `!important` 局所削減の詳細と段階的リファクタリング計画

**対象バージョン:** v1.30.68
**作成日:** 2026-08-20
**対象ファイル:** `CSS/base.css`
**前提:** Vanilla JS・既存DOM ID・イベント・PWA挙動を維持し、`!important`を一括削除しない。

## 1. 今回H6で削減した3件の詳細

v1.30.68では、トップバーの通常時戻るボタンに限定して、`!important`を3件削除した。対象は`.c-topbar__back-button`の表示有無やモバイル特例ではなく、PC・通常状態の純粋な見た目の指定である。

| プロパティ | 変更前 | 変更後 | 変更理由 |
|---|---|---|---|
| `padding` | `.c-topbar__back-button { padding: 0.25rem 0.6rem !important; }` | `.c-topbar .c-topbar__back-button { padding: 0.25rem 0.6rem; }` | 標準ボタンの余白と区別する必要はあるが、通常時の部品固有セレクタで十分に優先できるため |
| `font-size` | `.c-topbar__back-button { font-size: 0.82rem !important; }` | `.c-topbar .c-topbar__back-button { font-size: 0.82rem; }` | トップバー内の戻る導線だけをコンパクトに保つ目的を、重要度ではなく親子関係で表現するため |
| `font-weight` | `.c-topbar__back-button { font-weight: 600 !important; }` | `.c-topbar .c-topbar__back-button { font-weight: 600; }` | 戻る操作の視認性を維持しつつ、標準ボタン規則への上書き方法を正常なカスケードへ戻すため |

変更後のセレクタは、`.c-topbar`と`.c-topbar__back-button`の2クラスを持つため、標準の`.c-button`または`.c-button--compact`の単一クラス規則よりも詳細度が高い。したがって、読み込み順に依存して`!important`で固定するのではなく、トップバーというコンテキストを明示して通常時のスタイルを優先できる。

> `main.css`では`base.css`が先に読み込まれ、標準ボタンを含む`components-standard.css`が後に読み込まれる。このため、単一クラスの`.c-topbar__back-button`だけでは後続規則と競合し得る。親コンテキストを加えた`.c-topbar .c-topbar__back-button`は、必要最小限の詳細度でその競合を解消する。

## 2. 今回保持した!importantとその理由

`!important`はすべて悪いわけではない。状態強制、狭幅専用の操作導線、第三者または既存の広いセレクタからの保護など、意図的にカスケードを遮断すべきケースがある。今回、次の規則は削除対象から除外した。

| 規則 | 維持理由 | 将来の扱い |
|---|---|---|
| `.c-topbar__back-button.hidden { display: none !important; }` | JavaScriptの`hidden`状態が、通常時の`display: inline-flex`より必ず優先される必要があるため | 共通の状態クラス方針を整備するまで維持 |
| `@media (max-width: 768px) { .c-topbar__back-button { display: none !important; } }` | スマホでは下部コンテキストバーの戻る導線へ一本化する既存UXを保護するため | P38の戻る導線契約を維持し、アプリシェル全体を扱う別リリースで検討 |
| `.c-sidebar__sync-row .c-popover`の位置・重なり指定 | サイドバー下部にあるポップオーバーの位置・重なりが汎用ポップオーバー規則を確実に上書きする必要があるため | ポップオーバーの責務を`components-system.css`へ集約してから局所移行 |
| `body.role-read-only ...`の権限制御 | 保護者モードで編集・危険操作を確実に無効化または非表示にするため | CSSだけに依存しないアクセス制御を確認後、表示目的と権限目的を分離 |

## 3. base.cssの現状

v1.30.68時点で、`base.css`の`!important`は**279件から276件**になった。分布上、最大の集中はモバイル向けの`@media (max-width: 768px)`で186件、次いで非メディア規則で76件である。小型端末向けの420px以下には11件、1200px以下には2件、520px以下には1件が残る。

| 領域 | 件数 | 主な性質 | リスク評価 |
|---|---:|---|---|
| 通常規則（メディア外） | 76 | 権限制御、ポップオーバー、個別カード、共通操作部品 | 中。詳細度の整理で減らせる候補がある |
| `max-width: 768px` | 186 | トップバー、ボトムナビ、戻る導線、モバイルメニュー、画面収容 | 高。片手操作・Safe Area・画面幅に直接影響する |
| `max-width: 420px` | 11 | 最狭幅の収容調整 | 高。長い日本語ラベルで再確認が必要 |
| `max-width: 1200px` | 2 | 中間幅の表示調整 | 低。対象が限定的 |
| `max-width: 520px` | 1 | 小型幅の例外 | 低。単独規則として確認可能 |

特に、モバイルの`.c-bottom-nav`、`.c-context-bar`、`.c-topbar`は、固定配置、Safe Area、タップターゲット、表示・非表示を同時に扱う。そのため、件数が多いことだけを理由に削減対象にしてはならない。一方で、`.mobile-more-item`、`.c-sidebar__sync-button`、`.c-practice-card__actions`のような通常の部品装飾には、セレクタ構造やCSS層を整えることで安全に減らせる可能性がある。

## 4. リファクタリング原則

### 4.1 目的別に分類してから変更する

各`!important`を、**状態強制**、**レスポンシブ配置**、**権限制御**、**部品装飾**、**レガシー競合回避**の5分類に登録する。分類不能な宣言は削除候補ではなく、まず依存関係の調査対象とする。

### 4.2 優先順位は「CSS層 → セレクタ設計 → 状態クラス」の順で解決する

通常の見た目競合は、最初に正しいCSSファイルへ規則を移し、次に親コンテキストまたはBEM修飾子で意図を表現する。それでも状態切替を確実に保証する必要がある場合だけ、狭いセレクタに限って`!important`を残す。

### 4.3 ブレークポイントを統合しないまま宣言を動かさない

`base.css`には同じ`max-width: 768px`が複数存在する。これは長期的に集約対象だが、最初の段階では規則の移動と`!important`削減を同じ変更に混在させない。変更原因と画面回帰の切り分けを可能にするためである。

### 4.4 ひとつのリリースで扱う領域を一つに固定する

アプリシェル、モバイルメニュー、同期ポップオーバー、権限制御、練習カードを同じリリースで扱わない。各リリースは、一つのユーザーフローまたは一つのコンポーネント群だけに限定する。

## 6. 各リリースの品質ゲート

各リリースでは、削除前に対象セレクタとその出現画面を台帳化し、削除後に次の品質ゲートをすべて通す。`!important`の件数だけは成果指標にせず、表示・操作・権限が維持されていることを完了条件とする。

```bash
node --check app.js matches.js settings.js practices.js library.js tactics.js
node tests/run-contract-tests.mjs
node tests/run-responsive-validation.mjs
bash scripts/audit-legacy-css.sh
git diff --check
```

追加で、対象コンポーネントについて次を必須とする。

| 対象 | 追加検証 |
|---|---|
| トップバー・戻る導線・ボトムナビ | P38、PC／768px／420pxの視覚確認、戻る先の文脈復元 |
| モバイルメニュー | 保護者／コーチ、ライト／ダーク、44px以上のタップ領域 |
| 同期ポップオーバー | 同期成功・進行中・エラー、閉鎖、重なり順、キーボード操作 |
| 練習カード | 全操作ボタン、長いメニュー名、少人数／多数参加者、狭幅での収容 |
| 権限制御 | 非表示だけでなく、イベント実行・画面遷移・データ操作が抑止されること |

## 7. 完了条件

`base.css`の`!important`をゼロにすることは完了条件にしない。完了条件は、各コンポーネントの責務が適切なCSS層へ配置され、通常装飾が正常なカスケードで解決され、`!important`が状態強制・安全な権限制御・安全なレスポンシブ例外に限定されることである。各削減はP35へ再導入防止契約を追加し、回帰しにくい設計へ変換する。
