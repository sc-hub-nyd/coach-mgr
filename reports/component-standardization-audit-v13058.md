# CoachMgr 部品標準化監査報告書

**対象版:** v1.30.58  
**監査日:** 2026-08-19  
**対象:** `index.html`、全トップレベル JavaScript、`CSS/*.css`、既存のレガシーCSS監査台帳

## 結論

今回のラベル形状統一により、状態表示は `c-status` を唯一の正本とする状態へ大きく前進しました。しかし、アプリ全体では**標準部品と旧来の画面固有実装が併存**しています。特に、ボタン・フォーム・カード・モーダルという横断的な基盤要素、ダッシュボードのウィジェット構造、選手・練習・同期管理の一覧／操作面には、既存の `c-*` 部品で吸収できる実装、または新たな共通部品として切り出すべき実装が残っています。[1] [2]

監査で検出した画面固有クラスは、すべてが直ちに削除対象ではありません。作図キャンバスや戦術ピッチの座標・幾何形状のように、機能領域に閉じた表現は**ドメイン固有部品として保持することが適切**です。一方で、複数画面にまたがる操作・入力・カード・リスト・オーバーレイは共通化の効果が高く、優先して整理すべきです。

> **判断原則:** 形状や意味が複数画面で共通するUIは `c-*` の唯一の正本へ集約し、ドメイン固有のデータ表現・キャンバス幾何・一回限りの画面構成は、既存機能を壊さない範囲で明確なスコープを持つ部品として残します。

## 監査方法と測定上の注意

CSSからクラス定義を抽出し、`index.html` とトップレベル JavaScript 内のテンプレート・DOM操作に出現する同名トークンを照合しました。次に、`c-*`／`l-*`／`u-*`／状態名を除いたクラスを「画面固有候補」とし、既存のレガシーCSS台帳、インライン `style`、`!important` を合わせて確認しました。

この方法の候補数は、擬似状態・互換クラス・一回限りの構造クラスも含む**探索母集団**です。従って、候補数そのものを技術的負債の件数とは見なしません。本報告では、実行時参照、既存共通部品との重複、影響範囲、ドメイン固有性を踏まえて優先順位を付けています。

| 観点 | 測定値 | 解釈 |
|---|---:|---|
| `c-*` のCSSセレクタトークン | 222 | 共通部品の基盤は存在する。ただし、旧実装の置換は完了していない。 |
| 画面固有候補クラス | 587 | 探索母集団。状態・機能専用クラスも含む。 |
| 実行時参照がある画面固有候補 | 398 | 移行可否を精査すべき実使用候補。 |
| 既存台帳上のレガシー部品定義／参照 | 24／11 | 名簿、PK、フィルムストリップに明確な残課題がある。 |
| `u-ext` 定義／参照 | 133／204 | 未使用ではないため、一括削除は不可。機能単位で共通部品へ吸収する必要がある。 |
| `style="..."` 属性 | 533 | 静的装飾、テンプレート生成、状態制御が混在。大部分はクラスへ移せる可能性がある。 |
| `element.style` 等の操作 | 166 | 動的幅・座標・可視化も含む。全件をクラス化せず、状態表現だけを優先する。 |
| `!important` | 467 | `base.css` 279件、`dashboard.css` 121件、`components.css` 48件、`drawing.css` 18件、標準部品層 1件。層の優先順位が安定していない兆候。 |

## 現在も残る主な未標準領域

### 優先度P0 — 基盤プリミティブの二重系

`btn`／`btn-primary`／`btn-secondary`／`btn-sm`、`form-control`、`form-group`、`card`、`modal`／`modal-overlay` は、実行時参照が非常に多い一方で、`c-form-field`、`c-modal`、`c-action-group`、`c-data-list` と並存しています。たとえば `btn` は370回、`form-control` は143回、`modal` は73回、`card` は74回の参照が検出されました。標準部品層にも `.btn`／`.form-control` への互換セレクタが残るため、「標準部品を使っているように見えるが、実際は旧基盤に依存する」状態です。[1] [2]

| 対象 | 既存の正本候補 | 推奨方針 | リスク |
|---|---|---|---|
| ボタン群 | `c-action-group`、現行`.btn` | まず `.btn` を**互換基盤**として文書化し、`c-button` の役割・サイズ・状態を定義する。マークアップの一括改名は後段で行う。 | 高 |
| 入力群 | `c-form-field`、`c-form-grid` | `form-control`／`sl-input` を `c-form-field` の内部要素・互換別名へ整理し、ラベル、ヘルプ、エラー、密度を一元化する。 | 高 |
| カード群 | `c-card`、`c-metric`、`c-data-list` | 汎用カードを `c-card`、数値を `c-metric`、反復行を `c-data-list` に分類し、`card` の意味の過積載を解消する。 | 中 |
| モーダル群 | `c-modal` | `modal`／`modal-overlay` と `c-modal` の二重構造を解消し、ヘッダー、本文、フッター、閉じる操作を `c-modal` に統一する。 | 高 |

### 優先度P1 — 既存共通部品へ直結できるレガシー行・カード

既存の台帳で明示されている `.attendance-roster-row`、`.pk-kicker-row`、`.filmstrip-card` は、すでに `c-roster-row`、`c-data-list`、`c-action-group` と部分的に共存しています。DOM ID・イベント・入力制約を維持しながら段階的に置き換えられるため、リスクに対して効果が高い領域です。[2] [3]

| 対象 | 現状 | 置換先・新設候補 | 優先理由 |
|---|---|---|---|
| 出欠名簿 | `.attendance-roster-row` が4箇所参照、11定義トークン | `c-roster-row--attendance` | 既に共通名簿部品がある。 |
| PKキッカー | `.pk-kicker-row` と子要素が残存 | `c-data-list__item` + `c-form-field--compact` + `c-action-group` | 既存のP35契約にも構造が存在する。 |
| フィルムストリップ | 外枠は `c-data-list` 化済みだが、`filmstrip-card` 関連が残る | `c-media-sequence` または `c-data-list` の明示的バリアント | 時間・キャプション表示のラベル統一は完了済みで、次はカード構造が対象。 |
| 練習カード | `c-practice-card` と `practice-card-*` が併存 | `c-practice-card` の要素・バリアント | 同種の見出し、日付、詳細、操作群の重複を削減できる。 |

### 優先度P1 — ダッシュボードのカード／ウィジェット構造

`dash-*` は39クラス、約104個のCSSトークン、98件の実行時参照を持ちます。ランキング・予定・フォームバー・アラート・KPIは一部が `c-metric` や `c-data-list` に移行済みですが、ウィジェット外枠、ヘッダー、空状態、アクション、密度指定は画面専用規則に分散しています。[1] [4]

ダッシュボード固有の情報設計を失わないために、すべてを汎用カードへ押し込むのではなく、次の薄い合成部品を新設することが適切です。

| 新設候補 | 責務 | 吸収する既存規則 |
|---|---|---|
| `c-dashboard-widget` | 見出し、本文、補助操作、密度、空状態を持つウィジェット外枠 | `dash-rank-card`、`dash-next-event-card`、`dash-alert-banner` 等 |
| `c-dashboard-widget__header` | 見出しと右側アクションの整列 | `dash-form-header`、各種見出し規則 |
| `c-summary-strip` | 直近結果・予定の小型連続表示 | `dash-form-bar`、`dash-form-item` |
| `c-insight-panel` | 注意・提案・フィードバックの意味色パネル | `feedback-box`、`insight-*`、一部の `dash-no-data` |

### 優先度P2 — 設定・同期・保護者運用画面

設定画面には `sl-*`、同期には `sync-*`、保護者管理には `parent-*`、運用診断には `operations-*` が残っています。いずれも単なる色差ではなく、設定値・同期状態・権限というドメイン固有の情報を扱うため、完全な一般化は不要です。ただし、外枠、見出し、反復リスト、状態表示、操作配置は既存の `c-settings-section`、`c-data-list`、`c-status`、`c-action-group`、`c-empty-state` に集約できます。[2]

推奨する順序は、`sl-input`／`sl-row`／`sl-add-row` をフォーム基盤へ統合した後、同期履歴と保護者招待を `c-data-list` へ、最後に競合ダイアログ・運用チェックを `c-modal` と意味色パネルへ統合する流れです。同期の進捗やエラーは機能に直結するため、見た目だけの一括置換は行わず、既存の状態遷移を契約テストで固定してから移行します。

### 優先度P2 — 選手ノート・参加履歴

`player-notebook-*`、`player-participation-*`、選手詳細ページ固有のクラスは、各々の参照数は小さいものの、CSSトークン数が多く、1画面内にプレースタイル、成長メモ、評価、参加実績、集計が混在しています。これらは画面をまたぐ再利用よりも、**同一画面内での構造統一**が先です。

`c-section-header`、`c-metric-grid`、`c-step-list`、`c-data-list`、`c-empty-state` を組み合わせ、選手ノート固有なのは評価軸と時系列の意味だけに限定してください。新たに巨大な `c-player-notebook` を作るより、既存部品の合成と、必要最小限の `player-notebook` スコープへ縮小する方が保守しやすくなります。

### 優先度P2 — アプリシェル、ナビゲーション、ポップオーバー

`sidebar-*`、`topbar-*`、`bottom-nav`、`mobile-*`、`dock-*`、`sync-popover` はアプリ全体に影響する構造ですが、現在は主に `base.css` に集まり、同ファイルには `!important` が279件あります。レスポンシブ回帰の危険が高いため、最初にクラス名を変更するのではなく、**アプリシェルの契約を分離してから**個別規則を移すべきです。[4]

推奨する構成は、`l-app-shell`（大域グリッド）、`c-topbar`、`c-sidebar`、`c-bottom-nav`、`c-context-dock`、`c-popover` です。ナビゲーションの44px操作領域、保護者／コーチの権限制御、戻る文脈復元は、P38の既存契約を維持条件にします。

### 優先度P3 — 作図・戦術のドメイン固有UI

`anim-*`、`side-info-*`、`dock-*`、`drawer-*`、`tactical-pitch`、`pitch-node`、ゴール・ペナルティ・コーナーの幾何クラスは、描画座標・キャンバス・ドラッグ操作・戦術ボードという固有要件を持ちます。これらを一般的なカードやリストへ無理に変換することは推奨しません。

標準化の対象は、作図の「周辺UI」に限定します。具体的には、ツールドックを `c-tool-dock`、右側情報を `c-inspector-panel`、クイックドロワーを `c-drawer`、設定ポップオーバーを `c-popover` として切り出します。ピッチの座標・選手ノード・矢印・領域は機能専用クラスとして維持します。

## 横断的な設計負債

### インライン装飾

`style="..."` は533件、JavaScriptの `element.style` 系操作は166件あります。数値に応じた幅、キャンバス座標、ドラッグ中の位置、色テーマのCSS変数のように、インライン指定が妥当なものもあります。しかし、`display`、`padding`、`gap`、`font-size`、`color`、`width:100%` のような静的な表現がテンプレート内に多数残っています。

対策は「インラインをゼロにする」ことではありません。次の三分類で置換してください。

| 分類 | 例 | 方針 |
|---|---|---|
| トークン化すべき静的装飾 | 余白、フォント、整列、通常色 | `c-*`、`l-*`、既存ユーティリティへ置換する。 |
| 状態として表すべき装飾 | 表示／非表示、選択、エラー、同期中 | `hidden`、`is-*`、`data-state`、`aria-*` で表現する。 |
| 実行時値が必要な装飾 | 進捗幅、座標、Canvas寸法、チーム色変数 | CSSカスタムプロパティまたは限定された `style` 操作を許容する。 |

### `!important` とカスケード競合

`!important` は合計467件で、特に `base.css` と `dashboard.css` に集中しています。これはコンポーネント化の不足というより、CSS層の責務が逆流している兆候です。標準化作業と同時に `!important` を一括削除してはいけません。まず同一目的の規則を一つの層へ寄せ、詳細度を下げ、対象コンポーネントのビジュアル回帰を確認してから、画面群ごとに削減します。

## 再発防止ルール

新規UIを追加する際は、次の順序で判断します。

1. 既存の `c-*` 部品とバリアントで表現できるかを確認する。
2. 複数画面・複数機能で再利用するなら、画面固有CSSではなく `components-standard.css` または `components-system.css` に部品契約を追加する。
3. 1つの機能に閉じる場合も、目的が分かるBEM構造とスコープを与え、汎用部品を上書きしない。
4. 静的な `style` 属性と `!important` は原則として追加しない。例外は実行時の数値・座標・テーマ変数に限り、理由をコードコメントまたは契約で残す。
5. 旧クラスを削除する前に、HTML、動的テンプレート、`classList`、CSS、テストの実行時参照がゼロであることを確認する。
6. 画面横断部品には、P35形式の存在契約と、該当する振る舞い契約を追加する。

## 推奨する次の着手

次の実装フェーズは、**波Aのうちモーダルとフォームから開始**することを推奨します。既存の `c-modal` と `c-form-field` がすでに存在するため、ゼロから抽象化を作る必要がなく、重複している `modal`、`modal-overlay`、`form-control`、`form-group`、`sl-*` の整理に直結するためです。ボタンの全面改名は参照数が大きく影響範囲も広いため、まずは互換仕様の定義と新規実装への適用から始めるべきです。
