# CoachMgr デザインシステム・レスポンシブ品質基盤 導入計画

## 目的

CoachMgrのUIを「見た目が揃っている」状態から、**画面幅・表示データ・モード切替・PWA更新の差異があってもレイアウトが破綻しにくい状態**へ移行します。対象は色や角丸の統一だけではありません。カード、フォーム、操作群、モーダル、固定ナビゲーションに明確な責務とレスポンシブ挙動を定義し、変更時に実データを使った検証で回帰を検出できるようにします。

> **設計原則**: 画面固有の例外ではなく、再利用可能な部品と明文化されたレイアウト契約で問題を解決する。例外が必要な場合も、どの画面幅・どの状態・どの部品に限定されるかを記録する。

## 現状の評価

CoachMgrにはすでにトークン、レイアウト、標準コンポーネント、ユーティリティという土台があります。一方で、歴史的な画面固有CSS、動的HTMLのインラインスタイル、複数箇所のメディアクエリ、強い優先順位の指定が併存しています。そのため、ある画面幅での局所修正が別幅の表示を上書きする余地があります。

| 領域 | 現状 | 改善方針 |
|---|---|---|
| トークン | 色・余白・角丸・影の変数が存在 | 意味トークンへ集約し、画面固有の数値を段階的に削減 |
| レイアウト | `l-stack`、`l-grid`などの基盤がある | カードヘッダー、フォーム行、操作群、固定ナビ回避をレイアウトプリミティブ化 |
| コンポーネント | `c-card`などの標準部品がある | Button、Card、Form Field、Action Group、Modal、Roster Rowを正式な部品群として定義 |
| 画面固有CSS | 既存機能との互換を保つため多い | 明確な移行対象を決め、部品化した画面から削減 |
| 検証 | DOMの横溢れ確認はある | サンプルデータを投入した画面キャプチャ比較を追加 |
| PWA更新 | Service Workerキャッシュが関係する | リリースごとにCSS・SWキャッシュを一体管理 |

## 目標アーキテクチャ

CSSは、下記の責務順で読み込む構成を維持します。後方の層が前方の層を安易に上書きしないことを原則とし、同じ部品の規則を別ファイルへ重複して置かないようにします。

| 層 | 責務 | 代表例 |
|---|---|---|
| Base | リセット、基本文字、アプリ骨格、アクセシビリティ | `base.css` |
| Tokens | 色、余白、角丸、影、レイヤー、操作領域 | `tokens.css` |
| Layouts | ページを組み立てるだけの汎用配置 | `l-stack`、`l-grid`、`l-cluster`、`l-page-safe-bottom` |
| Components | 意味と振る舞いを持つ再利用部品 | `c-card`、`c-button`、`c-form-field`、`c-action-group`、`c-modal` |
| Pages | 部品の組合せに限った画面固有の規則 | 設定、練習、試合、選手 |
| Utilities | 1つの目的だけを持つ例外 | `u-truncate`、`u-scroll-x` |

## 最優先で定義する部品契約

### 1. 操作群 `c-action-group`

練習カードのように、テキスト付き操作とアイコン操作が混在する領域です。画面幅ではなく**親コンテナ幅**を基準に、広いカードでは横並び、狭いカードでは2列、さらに狭い領域では共有・確定操作を全幅にします。操作群は本文や統計バッジと同じ行を共有しません。

| 幅区分 | レイアウト契約 | 受入基準 |
|---|---|---|
| Wide | 内容に応じた横並び | 日付・統計と重ならない |
| Compact | 2列Grid | テキスト付き主要操作を切り詰めず表示 |
| Narrow | 2列＋全幅の確定・共有操作 | 全ボタンが44px以上の操作高を持つ |

### 2. カードヘッダー `c-card__header`

カードの「タイトル・メタ情報」と「操作群」は別ブロックにします。小さなカードでは常に縦積みとし、カードの列数と無関係に安全な幅を確保します。これにより、タブレット横向きで2列カードになった場合も、ボタンが統計バッジの上に重なりません。

### 3. フォーム `c-form-field` と `c-form-grid`

ラベル、入力、補足文、必須表示を1つの部品として扱います。`min-height`は入力種別ごとに定義し、カード自体へ固定高を与えません。設定画面のように項目が縦に並ぶ場合は、グリッドの自動行を内容高にし、空白を作る`align-content`や固定高を禁止します。

### 4. 名簿行 `c-roster-row`

checkbox、選手名、出欠selectを個別の列として定義します。狭幅ではselectを次行へ移し、checkboxと名前は常に同じ操作単位として保持します。モーダルの固定フッターに隠れないよう、名簿スクロール領域の下端にフッター高さ分の余白を持たせます。

### 5. モーダル `c-modal`

モーダルは本文スクロールとフッターを分離します。ヘッダーとフッターは固定、フォーム内容だけをスクロールさせます。モバイルでは`dvh`とsafe areaを用い、保存・キャンセル操作は常に画面内に残します。

### 6. ページ安全余白 `l-page-safe-bottom`

固定ボトムナビゲーションがある画面は、個別ページで余白を都度計算しません。共通プリミティブがナビの実高さとsafe areaをもとに、リスト末尾へ下部余白を付与します。

## 導入ロードマップ

### フェーズA: 仕様の固定

最初に、部品台帳とレスポンシブ契約を作成します。対象は、Button、Action Group、Card Header、Form Field、Modal、Roster Row、Bottom Navigationです。各部品について、許可するバリエーション、最小操作サイズ、コンテナ幅別の配置、アクセシビリティ要件を1ページで定義します。

成果物は、`DESIGN_SYSTEM.md`、`RESPONSIVE_CONTRACTS.md`、コンポーネントごとの代表HTMLです。この段階では既存画面を大きく書き換えません。

### フェーズB: 共通部品の実装

次に、上記部品を`CSS/components-standard.css`と`CSS/layouts.css`へ実装します。`!important`を含む競合規則を部品単位で削減し、インラインのレイアウト指定をクラスへ移します。既存画面は、新しい部品を導入した単位だけ置換し、機能ロジックを変えないことを原則にします。

最初の移行対象は、今回崩れが発生した「練習カード」「練習編集モーダル」「設定フォーム」です。この3画面で部品契約を安定させてから、試合・選手・同期設定へ展開します。

### フェーズC: ページの移行

ページ単位ではなく、部品単位で移行します。たとえば練習画面には`c-card__header`と`c-action-group`を導入し、設定画面には`c-form-field`と`c-form-grid`を導入します。古いセレクタが新部品と同じプロパティを持つ場合は、移行完了時に削除します。

| 優先度 | 対象 | 導入部品 | 理由 |
|---|---|---|---|
| P0 | 練習一覧 | Card Header、Action Group、Safe Bottom | 現在の重なりが最も顕著 |
| P0 | 練習編集 | Modal、Roster Row、Sticky Footer | 小画面での入力・保存操作に直結 |
| P0 | 設定 | Form Field、Form Grid、Safe Bottom | 過大な空白と操作被りを解消 |
| P1 | 試合詳細 | Roster Row、Action Group | 同じ招集・出欠パターンを再利用 |
| P1 | 選手比較 | Data Row、Responsive Stat Layout | 狭幅の情報密度を安定化 |
| P2 | ダッシュボード・分析 | Summary Card、Data Grid | 既存機能を保ちながら段階置換 |

### フェーズD: 視覚回帰テスト

現在の横溢れ検証に加えて、テスト専用のシードデータを使います。選手12名、練習6件、長い場所名、操作ボタン5個、未回答・欠席を含む名簿を用意し、空状態だけでなく最も密度が高い状態を検証します。

対象幅は320px、390px、768px、1024px、1280px、1440pxとし、縦向き・横向きの両方を含めます。テストは次を失敗条件とします。

| 失敗条件 | 検出方法 |
|---|---|
| 横溢れ | `scrollWidth > viewport width` と画面外要素の検出 |
| 要素の重なり | 主要領域の矩形交差検査 |
| 固定ナビによる被り | リスト最終要素とボトムナビの矩形交差検査 |
| 操作サイズ不足 | 主要buttonの最小幅・高さ検査 |
| モーダル保存不能 | 保存・キャンセルボタンの可視領域検査 |
| 視覚差分 | 基準スクリーンショットとの差分確認 |

### フェーズE: 変更統制

新しい画面・部品を追加する際は、部品台帳に存在するものを優先します。新しいレイアウトパターンが必要な場合だけ、先に部品契約とテストケースを追加します。ページ固有CSSは「そのページにしか存在しないデータ表現」に限定し、ボタン、フォーム、モーダル、操作群の再実装を禁止します。

PWAリリースでは、アプリのバージョン、CSSクエリ、Service Workerのキャッシュ番号を同一PRで更新し、ユーザーが旧スタイルを受け続けないようにします。

## 具体的な開始手順

最初の実装単位は、練習カードと練習編集モーダルです。これらを`c-card__header`、`c-action-group`、`c-roster-row`、`c-modal`へ移行し、320px・横向きタブレット・デスクトップのスクリーンショットを固定します。次に設定フォームへ`c-form-field`と`l-page-safe-bottom`を適用します。

この順序なら、現在の画面の機能ロジックを保持したまま、問題が繰り返し出ているパターンから再発を止められます。以降の画面では、検証済みの部品を使うだけで、同じ余白・折返し・safe areaの判断を毎回書かずに済みます。

## 完了条件

デザインシステム導入の第一段階は、次を満たした時点で完了とします。

1. 練習一覧、練習編集、設定、試合詳細が共通部品を使用している。
2. 対象部品に重複したレイアウト規則や新規の`!important`がない。
3. 密度の高いシードデータを使用し、320pxから1440pxまで主要画面の横溢れ・重なり・固定ナビ被りがない。
4. PWA更新時にCSSとService Workerのキャッシュが同時に更新される。
5. 新しいUI変更は、部品契約と視覚回帰テストを通過しない限りmainへ統合されない。
