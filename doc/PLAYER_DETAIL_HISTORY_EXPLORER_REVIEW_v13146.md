# 選手詳細履歴エクスプローラー提案レビュー — v1.31.46時点

**レビュー日:** 2026-08-22
**対象:** `PLAYER_DETAIL_HISTORY_EXPLORER_PROPOSAL.md`
**基準リリース:** v1.31.46

## 結論

提案書の問題設定、すなわち「履歴を隠すのではなく、成長の事実を見つけ、振り返れるようにする」は妥当である。一方で、提案書はv1.31.45以前の構造を前提にしており、推奨案Bの中核であった年表・画面内検索・年度横断・月間の手掛かり・役割別の入口は、v1.31.46で既に実装済みである。

次期は「最新6件＋探索シート」へ戻すのではなく、現在の**学年 → 月 → 記録詳細**のドリルダウンを正本として強化するべきである。特に、ページ内の二重スクロールを解消し、構造化検索を増やし、未整備の出場試合履歴を同じ探索原則で設計する順序が、利用者価値・実装リスク・既存要件への適合の均衡がよい。

> **設計判断:** 「成長の年表」は読む経路、「記録を探す」は見つける経路として維持する。長大な履歴をモーダルやサイドバーへ退避させず、選手詳細の画面内文脈を保つ。

## 主要なレビュー所見

### 1. 最も重要な残課題は、内側スクロールである

年表はドリルダウン化されたが、`pd-notebook-timeline`は現在も`c-data-list--scrollable`を持ち、最大25remの内側スクロールとなる。学年・月を開いた後にページスクロールと年表スクロールが競合すると、提案書が指摘したモバイルの摩擦が残る。

年表の全月展開には戻さず、**開いている月だけを通常のページフローで読む**構造にするべきである。検索結果だけは20件単位の明示的な「さらに表示」で密度を制御し、自動無限スクロールにはしない。

### 2. 検索は新しいシートではなく、既存画面内モードを拡張する

v1.31.46の検索は、キーワード・種別・結果件数・条件クリア・年表への往復を既に持つ。次に必要なのは、年度、次の一歩の有無、スキル評価の有無という**少数の意味ある条件**である。条件はすべてボタンまたはselectで操作し、選択状態、結果件数、クリア操作、検索復帰状態を読み上げ可能にする。

### 3. 次の大きな価値は「出場の足あと」である

選手詳細の通算出場数は確認できるが、出場した試合を「経験の地図」としてたどる専用面はない。試合の件数が増えるほど、保護者は思い出したい試合を、コーチは特定の相手・結果・得点／アシストの試合を見つけにくくなる。

このため、育成年表を複製するのではなく、直近5試合の要約と画面内の「試合を探す」を組み合わせる。検索結果は、年度、相手、結果、得点あり、アシストありで絞り込む。過去年度の結果を開く際は、年表と同様に正しいワークスペースへ切り替え、既存の試合詳細・作図導線を維持する。

## H3の最小データ設計

`player-timeline-service.js`の年度横断アーカイブを基盤に、試合アイテムへ次の検索用正規化フィールドを追加する。保存済み試合データを移行せず、表示用に導出することを原則とする。

| フィールド | 導出元 | 用途 |
|---|---|---|
| `sourceSeasonId` / `sourceNendo` | 現行の年度横断アーカイブ | 過去年度の試合詳細を正しいワークスペースで開く。 |
| `opponent` | 試合の対戦相手 | 部分一致検索。 |
| `resultState` | 試合結果 | 勝ち・分け・負け・未入力の絞り込み。 |
| `goalCount` / `assistCount` | 選手に紐づく得点記録 | 得点あり・アシストありの絞り込みと小さな事実表示。 |
| `hasDrawing` | 既存作図の有無 | 作図導線を提示するかの判断。 |

## 着手前に固定すべき非機能条件

1. 新しい検索はサイドバー・モーダルを使わず、選手詳細内のコンテンツモードとして提供する。
2. 保護者は閲覧専用であり、検索・試合詳細・作図閲覧は利用できる。記録追加・削除はコーチだけに限定する。
3. 新しい一覧・フィルター・節目に直接色を指定しない。セマンティックトークンとローカルTablerサブセットを使う。
4. すべての結果リストに、空状態、件数通知、44px以上のタップ領域、キーボードフォーカス、縮退モーションを用意する。
5. PWAのprecacheへ新規サービスを追加し、年度横断データ・過去年度遷移・オフライン操作を契約テストで保護する。

## 見送るべき事項

フットボール年表の横断ピッチレーン、常時アニメーション、スコア化・バッジ・ランキング、無限自動読込は次期に採用しない。これらは本提案の「成長の事実を見つける」という目的よりも、表示上の複雑さ・操作コスト・アクセシビリティリスクを大きくするためである。
